# Define requirements

Read [the requirements model](references/requirements.context.md) and
[the component model](references/component-model.md). Use the consuming project's
purpose, personas, journeys, constraints and existing commissions as the starting
point. Preserve its authority mappings and stable IDs.

State the observable obligation and why it matters. Put satisfaction criteria in
the requirement; keep planned checks and actual observations separate. Distinguish
aspirational targets from binding thresholds, and define observation methods and
units for quantitative criteria. Do not invent thresholds to make a vague outcome
look measurable.

Refine ambiguous or unobservable statements before claiming they can be covered.
Use verification planning to expose ambiguity and missing criteria. Proposed
changes to received obligations return to their definition authority; local
refinement within a commission belongs to the receiving component.

Maintain the register using the shared reference. Record unresolved context and
proposed obligations explicitly. Do not turn guidance, an example, a check design
or a package upgrade into an agreed product requirement.

Use `decompose-and-allocate-requirements` for allocation, `plan-requirement-verification` for
coverage planning, and `change-requirements-and-contracts` for published obligation changes.
